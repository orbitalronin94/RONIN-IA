<div class="page"><p></p>
<p>Approach / Strategy
• Leverage heterogeneous architectures via Domain Specific Language (DSL) 
</p>
<p>and OpenACC
• Recognize that accelerator-based heterogeneous systems provide a promising platform to meet future 
</p>
<p>GEOS requirements.
• DSL : Programming language specialized to a particular domain
</p>
<p>• DSL adoption creates an opportunity to create portable and scalable code across multiple platforms, 
including traditional CPU systems and accelerator-based systems, by abstracting away details of the 
computing architecture
</p>
<p>• For GEOS, we utilize the GridTools for Python (GT4Py) DSL
• Incorporate a GT4Py port of Geophysical Fluid Dynamics Laboratory’s 
</p>
<p>(GFDL) dynamical core (FV3) created by Vulcan / Allen Institute for AI (AI2) 
into GEOS
</p>
<p>• GT4Py-ported FV3 (gtFV3) is a non-hydrostatic code used for global storm-resolving modeling
• Leverage DSL without extensive investment in code rewriting / refactoring</p>
<p></p>
</div>
<div class="page"><p></p>

</p>
<p>• GridTools
</p>
<p>- C++ DSL
</p>
<p>- Express “stencil”-like patterns concisely
</p>
<p>- Multiple backends - OpenMP(CPUs)/CUDA/HIP
</p>

</p>

<p>GEOS-gtFV3 Performance Strategy
</p>
<p>• Many-processes vs Many-threads
• GEOS uses many-processes paradigm: one CPU core per task, with problems divided 
</p>
<p>in smaller problems.
• GPUs are built for many-threads paradigm: one GPU per problem computed across 
</p>
<p>many-threads, with the bigger problem size that fits memory.
</p>
<p>• Due to the hybrid nature of our work, we need solutions that can do both
• Many-processes on one GPU (Nvidia’s MPS).
• Different domain decomposition for physics and dynamics:
</p>
<p>• SI Team is working on this.
• Allow for best usage of each hardware: GPU is given the entire problem at once, 
</p>
<p>CPU is given a smaller chunk of the problem.</p>
<p></p>

<p>OpenACC for Physics
• Why OpenACC?
</p>
<p>• Development remains in Fortran
• Flexibility : GT4Py structures code based on stencil computations, making it less flexible if an 
</p>
<p>algorithm doesn’t map into a stencil.
• What about “proprietary-ness”?
</p>
<p>• OpenACC may not be the final solution since it’s (mostly) NVIDIA-centric and OpenACC compilers 
(generally) are not available or less optimal for non-NVIDIA GPUs. 
</p>
<p>• The OpenACC implementation can guide development of an OpenMP-offloading implementation due 
to the relatively similar feature set of both programming models.
</p>
<p>• General Porting Methodology
• Create a CPU-based standalone code of physics schemes that verifies with input and output data 
</p>
<p>generated from GEOS runs that call the physics schemes
• Apply OpenACC to parallelizable code sections within the CPU-based standalone code
• Verify that data computed from OpenACC standalone code closely matches GEOS generated data 
</p>
<p>from CPUs</p>
<p></p>
